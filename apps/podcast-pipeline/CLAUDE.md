# Gotchas

- `supabase/migrations/` and `supabase/schema.sql` are a frozen snapshot as of migration 035; parity tests read them in place. Current schema truth is the live database plus root `supabase/migrations/` (see CONTRIBUTING.md "Adding a database migration").
- **Telegram env vars are namespaced.** This service uses `PIPELINE_TELEGRAM_*` (bot token, webhook secret, allowed user IDs) deliberately so it does not collide with `apps/account-engine`'s `TELEGRAM_*` bot. Do not introduce unprefixed `TELEGRAM_*` vars here — they would be read by both processes.
- **Webhook is fire-and-forget.** `/telegram/webhook` returns 200 immediately and then runs `runIngestPipeline` in the background. Adding `await` on the pipeline call from the handler breaks Telegram's webhook timeout contract — keep new long-running work behind the same fast-ack pattern.
- **Video renders live in their own process.** `src/index.ts` serves HTTP and runs ingest; `src/worker.ts` runs the video worker, and they deploy as separate Fly process groups (`app` on shared CPU, `render` on dedicated CPU — see README). `bootstrap()` does not start a worker unless asked (`startVideoWorker: true`). Do not move rendering back into the API process: ffmpeg starves the event loop until `/health` times out and Fly drops the instance from the proxy pool. `heavyWorkCoordinator` still guards a single-process setup, but it cannot coordinate across the two groups — that separation is the point.
- **Resumability is load-bearing.** Fly keeps one `app` machine running so the webhook is always reachable, but deploys and restarts can still interrupt ingest. Each pipeline stage commits its result to Supabase before advancing, and the next submission of the same URL resumes from the latest committed stage. New pipeline stages must persist their output before yielding, or resume will silently lose work.
- **The render group is on demand — that is its only mode — and its wake-up test mirrors the claim RPCs.** `src/worker.ts` exits `0` on an idle queue unconditionally, and `src/services/render-capacity.ts` (in the always-on API process) starts the machine again. `readFlyMachinesConfig()` needs exactly the platform's `FLY_APP_NAME` plus `PIPELINE_FLY_API_TOKEN` (Infisical prod → `env:sync` → Fly). **Never reintroduce a feature flag or an always-on fallback here**: a missing token on Fly has to stay a boot-time configuration error, because the fallback that was deleted did nothing at all once the machine had already stopped itself — renders stalled silently from 2026-08-24 to 08-26 behind one boot log line. `evaluatePendingRenderWork` deliberately reproduces the `WHERE` clauses of `claim_episode_video_v2` / `claim_episode_video_visual_v2` — the `visual_version` fence, the completed-visual join, the attempt/backoff limits, and expired-lease `processing` rows. **Change the claim RPCs and this test together.** Looser here means the machine wakes, claims nothing and idles out on a loop; tighter means jobs sit on a stopped machine that nobody ever starts. Rows in `processing` past their lease are only reaped inside the claim RPCs, which is why they count as pending work rather than as work in progress.
- **`exit(0)` is what stops the render machine.** It works because the `render` group's restart policy is `on-failure` (declared explicitly in `fly.toml`). Switching it to `always`, or handling the idle path with a non-zero exit, turns the cost saving into a restart loop.
- **The cost ledger must never be able to fail the pipeline.** `recordPipelineRun` (`src/services/ops-ledger.ts`) swallows every error into one `[ops-ledger]` line plus a Sentry `warning` and resolves. Do not let a ledger write throw into ingest or a render — the money was already spent by the time it runs. Warning rather than silence is the other half of that rule: a ledger that quietly never writes looks exactly like a pipeline that never ran.
- **`fly.toml`'s render machine and `RENDER_MACHINE_SHAPE` change together.** Fly gives the worker no runtime signal for the machine it is on, so the shape is a constant in `src/services/ops-ledger.ts` and `ops-ledger.test.ts` parses `fly.toml` to prove they still agree. Resizing the `render` group also needs a new `ops.cost_rates` version (close the old row's `effective_to`, insert a new one) — never edit a rate row in place, or every historical render reprices.
- **Supabase schema is `from_fed_to_chain`, not `public`.** New queries must respect `SUPABASE_DB_SCHEMA` — defaulting to `public` will hit the wrong tables.
- **`social:daemon` is the canonical social production loop.** It runs on the local Mac because X/Rednote depend on persistent browser sessions. One daemon owns completed-localization discovery, durable enqueue/scheduling, platform publishing, standardized metric snapshots (`1h` / `6h` / `24h` / `72h` / `7d`), experiment reporting, and periodic strategy refresh. Social job and post identity is `(episode, platform, language)`; recovery must never let evidence for one language complete or suppress another. Do not split metrics or publishing into required companion processes. `social:publish` and `social:metrics` are break-glass/debug commands only. `apps/control-center` is a read-only optional UI and must stay lifecycle-independent so a dashboard port failure can never stop publishing or metrics. Preserve the durable first-start anchor, DB lease/owner fencing, and the rule that missed early metric windows are not backfilled with later observations.
- **Tests target the Hono app directly via `app.request(...)`** (see `src/index.test.ts`). No HTTP server is started in test mode.
- **Fish Audio is the only TTS provider, and that is code-owned.** `src/services/tts.ts` is a thin facade over `src/services/tts/fish-audio.ts`; there is no provider dispatch, no `TTS_PROVIDER` env, and no Google TTS. `getTtsConfig()` fails closed when `FISH_AUDIO_REFERENCE_ID` is missing rather than degrading to another voice. Adding a second provider means reintroducing dispatch deliberately — do not add a provider branch to keep some other change convenient.

## Audio section invariant

Do not concatenate language classroom audio into the main episode audio.

The canonical contract (per-language classroom, refactored 2026-08) is:

- `episode_localizations.hls_url` / `r2_prefix` stores main article narration only.
- Each `language_classrooms` row owns its **own** monolingual `script` (target-language-only narration) and its **own** independently-synthesized `hls_url` / `r2_prefix`. This per-language HLS is the canonical classroom artifact, not `episode_localizations.classroom_hls_url`.
- `episode_localizations.classroom_hls_url` / `classroom_r2_prefix` is now a **derived** artifact: the per-language classroom MP3s are concatenated (in target order) into one combined HLS at zero extra LLM/TTS cost. New episodes still produce it so `completed`-status checks, RLS policies, video-eligibility checks, and pre-refactor app builds keep working unmodified. Never derive it any other way (e.g. re-synthesizing a combined script).
- The mobile app plays main + one classroom section per target language as sequential playback sections within the same logical episode (language "chips" inside the Classroom tab select which target). Older app builds that only know the combined URL keep working off the derived artifact.
- Main and classroom playback speeds are intentionally independent. Classroom defaults to 1.0x.
- For a localization with configured classroom targets (currently canonical `zh-Hant` targeting `ja` and `en`), `completed` means the main HLS, every required per-target classroom HLS, **and** the derived combined HLS all exist. A status value alone is not evidence that audio is complete.
- Missing classroom lessons/scripts, failed classroom TTS for any required target, failed classroom concatenation, or a missing per-target or combined classroom HLS must fail ingest. Never publish a successful main-only canonical episode as a fallback.
- **The missing-target predicate that drives content (re)generation must stay presence-based**: a `language_classrooms` row existing for a target — regardless of whether its `script` is populated — counts as "not missing." This is what guarantees a previously-published episode (whose rows predate the `script` column and are therefore `script: null`) is never regenerated or re-touched by this refactor. Only flip this to a script-completeness check if you intend to force regeneration of every already-published episode; do not do that silently.
- Script backfill (writing a blank `script` on an existing row) happens **only** inside the audio-synthesis path, and only when that localization's classroom audio is not yet ready. It is unreachable for an already-completed row, by construction — do not add a code path that can backfill a script for a row whose audio is already ready.
- A previously completed row missing the combined `hls_url`/`r2_prefix`, or any required per-target classroom HLS, is incomplete and must resume by generating only the missing pieces without regenerating the main narration.
- Per-target `hls_url`/`r2_prefix` checkpoints on `language_classrooms` exist for observability and API reads only — **they are not a skip condition**. A resumed/retried ingest re-synthesizes TTS and re-packages HLS for every required target even if some were already checkpointed from a prior attempt. This is an accepted cost trade-off (~$0.01-0.02/episode via Fish Audio), not a bug; do not add per-target skip-if-checkpointed logic without an explicit decision to do so.
- `upsertLanguageClassrooms`'s payload never includes `hls_url`/`r2_prefix` — only content columns (`script`, `one_liner`, `keywords`, `llm_*`). A content-only upsert (e.g. script backfill) must never clobber an existing per-target audio checkpoint; keep the upsert column list scoped to content when adding fields.
- Demote an invalid completed row before repair, and persist each uploaded audio section (main, each per-target classroom, and the derived combined) under `audio_generated` before advancing. Promote to `completed` only after the persisted row contains all required HLS URLs.
- Database compatibility fallbacks must never remove classroom media fields from a completed write. Feed/RLS/video eligibility must enforce the same dual-audio condition against the derived combined URL (old contract) while the per-language rows carry the canonical per-target URLs (new contract).

Never reintroduce `concatMainWithClassroomAudio` or equivalent logic that appends classroom audio into the main HLS. `combineClassroomAudio` (per-language MP3s -> one combined MP3, used only to build the derived combined HLS) is a distinct, still-legitimate function — do not confuse the two.

All tests must exercise the same fail-closed classroom audio invariant as production. Do not add test-only switches that make canonical classroom audio optional.

## Language classroom content invariant

The audio-section invariant above governs the HLS _artifacts_. This section governs the _content_ those artifacts carry. The content layer has no schema/DB enforcement, so it is guarded by `src/services/llm.classroom.strict.test.ts` and the independent `scripts/check-classroom-contract.mjs` gate (wired into `lint`).

- **Grounding is required.** The classroom lesson generator (`generateLanguageClassroomsWithLLM` in `src/services/llm.ts`) must receive the title **and** the full article text **and** the podcast script. `LanguageClassroomInput` carries `articleText` and `script`; `buildLanguageClassroomUserMessage` must include the `文章內容：` and `Podcast 講稿：` blocks; the `ensureLanguageClassrooms` call site (`src/services/ingest/audio-stage.ts`) must pass `localization.raw_text` and `localization.script`. Narrowing the prompt to the title alone is a content regression, not a simplification.
- **Keyword selection is concept-based and shared.** Keywords are the episode's core financial/crypto concepts chosen from the article and script (thinking in `zh-Hant`), not substrings of the title or `oneLiner`. Every target language teaches the same shared concept set (same count and order). `oneLiner` remains the title translation used only as the classroom opening line — it and `keywords` stay source-language UI metadata, separate from the per-target `script`; do not blank out `meaning` on a keyword, since the app's parser silently drops the whole keyword entry if `meaning` is blank.
- **Each target's `script` is a purely target-language narration, grounded in the same article and podcast script.** The LLM must generate one `script` per target (~1.5-3 min of spoken narration) that (a) uses **only** the target language — no mixed-language segments — and (b) is written from, and covers, the same article/script content and the same shared keyword set as that lesson's `oneLiner`/`keywords`. A lesson whose `script` is blank is dropped rather than published with silent/empty audio.
- **Contract changes need explicit product sign-off.** Changing the system prompt, the input contract, or the lesson shape is a product decision. Do not alter it as an incidental part of unrelated work, and never rewrite the strict/contract tests in the same change to make a narrowed prompt or a language-impure/ungrounded script pass.
- **App-side dual-section contract.** Main audio and one classroom section per target language are playback sections of one logical episode. The app (`apps/app`) must play them sequentially (main -> each target's classroom, in order) with independent per-section speed (classroom defaults to 1.0x); see `apps/app/src/integration/podcastSections.ts` and its tests. Dropping classroom playback, or collapsing per-language sections back into a single combined section, on the client is the app-side equivalent of a main-only fallback.

## Social platform budget invariant

- **`(episode, platform)` is the release cohort and the scheduling unit; a language is only a lane inside it, and a lane must never move its cohort's release time.** `src/social/cohort.ts`'s `resolveReleaseCohortLanes()` is the single definition of which platform x language lanes an episode has; `daemon.ts` discovery, the media readiness barrier, and publish preflight all call it so they cannot disagree about the shape. Different platforms are independent releases: Rednote at 14:30 and YouTube at 17:15 are the same article, hours apart, on purpose.
- **Every pending lane of one `(episode, platform)` cohort shares one `scheduled_at`.** `enqueuePlatformCohort()` computes it once and `enqueueCohortJobs()` writes the same timestamp onto every lane of that platform. Do not reintroduce any cross-language gap constant (the deleted `MIN_CROSS_LANGUAGE_GAP_MS` and its sibling-anchor logic) -- that is the bug this replaced, where two languages of one article drifted hours apart in the queue.
- **Publish timing is code, not configuration.** `policy.ts`'s `PLATFORM_PUBLISH_POLICY` owns each platform's daily cap and candidate slots; `SocialStrategyConfig` carries copy guidance only. Timing used to live in `social_strategy_versions` and was never read -- the scheduler always used its own defaults -- and putting it back there would let a learner widen the cap it is supposed to be optimising inside. `social_waiting_media` holds a second copy of the _language_ policy, kept honest by `socialWaitingMediaPolicyMigration.test.ts`; change the two together.
- **A daily cap counts `(episode, platform)` cohorts per JST day across every language.** That is what stops a multilingual platform from publishing once per language and calling it one post. X is the only cap above one because its language experiment assigns each episode exactly one of `en`/`ja`, so its two daily posts are always two different episodes; the two languages swap slots every day (`crossoverPlan`) so neither language is permanently confounded with one time. A completed row whose `completed_at` falls on a different JST day than its `scheduled_at` does not reserve a day it never used (`occupiesPublishBudget`) -- reconciliation binds already-live posts to future slots.
- **A backlog is drained, never compressed and never dropped.** `nextBudgetSlot()` returns `null` past the eight-day horizon and the lane simply stays a candidate for a later tick. A lane whose slot has passed by more than `PUBLISH_SLOT_GRACE_MS` is moved forward by `reschedulePastDueJobs()`. Never reintroduce the deleted `skipOverdueSocialPublishJobs`: it marked such a lane `completed` with a `skipped: overdue` note, which recorded a post that never existed, and its grace period lived in an environment variable that was unset in practice.
- **Publishing runs only between 09:00 and 18:00 JST** (`SOCIAL_PUBLISH_WINDOW_JST`). Rednote and X drive real browser sessions on a Mac someone has to be able to watch fail. Outside the window `publishDueJobs()` claims nothing at all; the missed slot is rescheduled rather than served late.
- **A pending lane is claimable only when `scheduled_at` _and_ `next_attempt_at` are both in the past.** `claim_social_publish_batch` fences on both, so anything that reports or repairs the queue has to use the later of the two: `daemon-store.ts`'s `jobNextAt()` for the queue log, and `rescheduleSocialPublishJob()` for recovery, which writes the new slot onto both columns. Measuring "already due" on `scheduled_at` alone is what let one lane print `due now` every tick for 16 hours while it was never claimable.
- **A platform cohort only enqueues once every language _that platform_ needs is ready.** `enqueuePlatformCohort()` computes required languages from `resolveReleaseCohortLanes()` and ready languages from `listSocialPublishCandidatesForEpisodes()` (deliberately unfiltered by the discovery anchor, unlike `listSocialPublishCandidates()`, so a localization that finished ready before the anchor still counts). Missing a required language blocks that platform -- never enqueue "whatever is ready now" as a partial release -- but it must not block a platform whose own language has been ready for days.
- **Publishing is fail-fast.** `publish.ts`'s `publishSocialPlatforms()` throws a `SocialReleaseFailureError` (see `publish-error.ts`) on the first transport, local-state, or `social_posts` telemetry failure; it does not record a soft failure and continue to the next platform. `daemon.ts`'s `finalizePublishOutcome()` throws the same way when a publish reports success but the daemon's own `social_posts` verification can't find the row. Whichever lanes already published before the failure stay published; nothing after the failure runs this tick.
- **`reconcile`, `reschedule`, `discover`, and `publish` are fatal; only `metrics`, `account snapshots`, `strategy`, and `experiment report`/`queue summary` may isolate.** The first group can leave a cohort's lanes disagreeing about what actually published if swallowed; the second group is purely observational. A failure in the first group must propagate out of `runSocialDaemonTick()` uncaught -- do not wrap it in `isolate()`. The `isMainModule` entry point at the bottom of `daemon.ts` is what turns that into `console.error` + a best-effort Telegram notice (`buildSocialReleaseFailedMessage`) + releasing the pid lock + `process.exit(1)`.
- **`social:daemon` must never be a watch runner in production.** `tsx watch` auto-restarting past a fatal error defeats the invariant above. `apps/podcast-pipeline/package.json`'s `social:daemon` script runs plain `tsx`; `social:daemon:watch` (auto-restart) is a separate, explicitly debug-only script, and the root `package.json` passthrough for it must stay named `social:daemon:watch`, never shadow `social:daemon`.
- **There is no cross-episode fence, and reintroducing one would deadlock the queue.** The deleted `listPartiallyPublishedCohorts()` held every other episode shut until a half-published one finished, which was right while all five lanes shared one timestamp. Under per-platform budgets a partially published episode is the steady state, so a fence on it would block the queue against its own schedule. `publishDueJobs()` claims whatever is due, unnarrowed; `claim_social_publish_batch` is called with owner and time only.
- **Rednote hashtags are platform topic entities, never literal `#` text.** `rednote-playwright.ts` types each tag into the TipTap editor, accepts the exactly-matching suggestion row (`#creator-editor-topic-container .item`), and verifies the resulting `a.tiptap-topic` inside the editor -- the same anchor is mirrored into a preview region, so an unscoped read counts every topic several times. A 「新建话题」 row is a rejection, not a candidate: accepting it creates a brand-new topic with no audience and an empty link, which is success-shaped and worth nothing. The query is converted to Simplified because topic search is script-sensitive and the two scripts are _different topics_ -- 「宏觀經濟」 had 8.3万 views against 「宏观经济」's 5.2亿. A tag with no matching topic is skipped **and backspaced out**, because Escape closes the popup but leaves the typed characters in the body as exactly the literal hashtag this replaced; if no tag attaches at all the publish fails at `attach_topics` rather than shipping a note with no topic. `PublishResult.hashtags` carries what actually attached and `record.ts` stores that, so the strategy learner never credits a tag that was never on the note. The editor never carries anything else: no prose body, only the `#`-typed topic anchors described above. The real submission's `desc` field is therefore exactly those topic anchors concatenated (e.g. `#區塊鏈#SEC#監管`) -- that is expected, not evidence a body write was skipped.
- **Rednote notes publish title + topic entities only, with no prose body -- a 2026-08-27 limiting-diagnosis experiment.** Roughly 39% of Rednote notes were shipping to zero views with no rejection signal from the platform (`review_status` stayed `visible`), and the failure was bimodal -- a note either reached the recommendation pool or never did, with nothing in between -- which points at publish-time limiting rather than unpopular content. This change removes the prose body as the first variable to isolate: `createRednoteJob` (`publishers.ts`) and `createPlaywrightRednotePublisher` (`rednote-playwright.ts`) no longer send one, and `PublishResult.body` (default `''` for Rednote) is what `record.ts` writes to `published_body` instead of the composed draft. `generated_body` still stores the LLM's full draft -- `copy.ts` and `prompts/social/rednote.md` are unchanged on purpose -- so the two can be compared once the experiment is judged. Migration `20260828100000_allow_blank_rednote_published_body.sql` relaxed `social_posts_published_body_check` to allow a blank `published_body` for `platform = 'rednote'` only; every other platform still requires a non-blank body. Do not restore the body send as an incidental part of unrelated work -- reintroducing it silently reopens the exact variable this experiment isolates.
- **A Rednote field is only written when the SPA's own state says so, never when the DOM does.** `inputValue()` on the title returns whatever was just written to it, so it cannot detect the real failure: a write landing while the form re-renders (which attaching topics and setting the declaration both cause) sets the DOM value and never reaches the model, and the note is created with `title: ""`. That shipped untitled notes for weeks behind a check that never went red. `writeTitle()` verifies against the field's own character counter (`.count-tip`, a descendant of the same `.input` block as the field, rendered as `11 / 20`, absent as a whole element while the model is empty -- all three measured against the live form on 2026-08-27) and rewrites up to three times before failing at `fill_title`. Do not replace that with a DOM read-back, and apply the same reasoning to any new field: verify against something the SPA renders from its own state. **The acceptance condition is that the counter exists and reads above zero -- never that it equals `Array.from(title).length`.** Rednote weights a half-width character at half a full-width one, so it counts `AI代理不等於公鏈繁榮？` (twelve code points) as `11 / 20`; an equality check made every title carrying Latin text or digits fail `fill_title` forever the first time it met the real form, and because `publish` is fatal that took the release cohort down and held every queued episode shut behind it. The empty-model bug this check exists for shows up as an _absent or zero_ counter, never as off-by-one, so the counting model was never something the publisher needed to know: a disagreeing count is logged as `title_count_mismatch` and a missing counter stays fail-closed. Do not tighten this back to equality, and do not derive a test's fake counter from the publisher's own formula -- that tautology is exactly what let the equality check ship. `readTitleField()` is exported so the test runs the shipped traversal against the live form's markup in jsdom, and it is serialized into the page by `Locator.evaluate`, so it must stay free of imports, module constants, and calls to neighbouring helpers.
- **Every Rednote note declares itself as AI-synthesized.** `declareAiContent()` opens the 「添加内容类型声明」 select, picks 「笔记含AI合成内容」, and waits for the `.d-select-description` that proves it stuck; it fails the publish rather than logging and continuing, because a skipped declaration is invisible after the fact. This is a compliance step about how the video was made, and is unrelated to AI as a subject -- which is never a risk.
- **The Rednote copy gate has two layers, and neither is a topic blacklist.** `prompts/social/rednote-risk-rules.md` is the single source for the four investment-direction red lines; it is appended to the writer's Rednote block **and** read by the judge, so the two cannot drift. `asset_allocation_advice` and `market_timing_advice` are lexical and are caught by `lexicon/asset-allocation.ts` / `lexicon/market-timing.ts` at both existing gate points. `political_market_speculation` and `strong_prediction_unattributed` are framing, so `rednote-semantic-risk.ts` judges them with one LLM call inside `copy.ts`'s existing three-attempt loop -- a verdict of risk becomes the next attempt's retry reason. That judge is **fail-closed** on its own failures (`reason: 'unavailable'`, distinct from `'risk'`): a gate that fails open is the exact silent failure it exists to prevent. Do not answer a zero-view post by adding its subject (AI, Bitcoin, a named politician) to a term list -- suppressing a topic is the learner's job, and the AI note that also scored zero is pinned as a passing fixture precisely to stop that.
- **Guarding tests.** `slot-policy.test.ts`, `daemon-cohort-schedule.test.ts`, `daemon-cohort-media-barrier.test.ts`, `daemon-cohort-serialization.test.ts`, `publish.test.ts`, `daemon-release-fatal.test.ts`, `daemon-reconcile-*.test.ts`, `daemon.test.ts`, `daemon-store.test.ts`, `daemon-store-queue-snapshot-timing.test.ts`, `strategy-refresh.test.ts`, `socialWaitingMediaPolicyMigration.test.ts`, `rednote-playwright.test.ts`, `rednote-semantic-risk.test.ts`, and `lexicon/index.test.ts` are what would catch a regression on any bullet above.
